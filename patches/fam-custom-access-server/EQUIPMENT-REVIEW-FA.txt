# نسخهٔ سرور — طراحی جدید بررسی تجهیزات

تاریخ: ۲۰۲۶-۱۰-۱۸

بستهٔ نصب روی **سرور مرکزی موجود Windows / IIS / Python**:
`FAM-Custom-Access-SERVER-Patch.zip`، با فایل SHA256 مجزا.
این ZIP، فایل HTML نمایشی نیست؛ رابط احرازشدهٔ واقعی و ۲۳ فایل payload از سورس سرور داخل بسته‌اند. نصب تازه روی سرور خالی یا Docker image نیست. فایل‌های LOCAL در این انتشار بازسازی نمی‌شوند.

## نصب و حفاظت داده

۱. ZIP و فایل `.zip.sha256` را دانلود کنید و هش ZIP را با `Get-FileHash .\FAM-Custom-Access-SERVER-Patch.zip -Algorithm SHA256` تطبیق دهید.
۲. ابتدا روی کپی تستِ نصب موجود، بکاپ مستقل و قابل‌بازیابی از SQLite و تنظیمات فعلی بگیرید. برنامهٔ updater هم بکاپ و کنترل manifest خودش را انجام می‌دهد؛ این جای بکاپ مستقل را نمی‌گیرد.
۳. ZIP را در پوشه‌ای جدا Extract کنید. `README_FA.txt` را بخوانید و `APPLY-CUSTOM-ACCESS-UPDATE.cmd` را با Run as administrator اجرا کنید. مسیر پیش‌فرض نصب `C:\FAM` و داده `C:\FAMData` است؛ برای مسیر سفارشی از پارامترهای فایل PowerShell مطابق README استفاده کنید.
۴. پس از راه‌اندازی، مرورگر را Refresh و دوباره وارد حساب شوید. به فضای تجهیزات و «بررسی تجهیزات» بروید؛ کادر «IP یا نام محل» و درخت روتر/سوئیچ باید دیده شوند. marker رابط: `FAM-EQUIPMENT-REVIEW-20261018`.
۵. قبل از هر عملیات واقعی، دسترسی‌ها، موجودی، اثرانگشت‌های SSH و وضعیت سرویس را در محیط تست بازبینی کنید. rollback کد، دیتابیس را به گذشته برنمی‌گرداند.

دیتابیس تولیدی، رمز، فایل تنظیمات واقعی، known_hosts واقعی، کلید خصوصی، log، محیط مجازی و wheel داخل بسته نیست. بسته حاوی حساب اتصال تجهیزات نیست. نام کاربری و رمز اتصال فقط هنگام ورود به فضای تجهیزات در حافظهٔ نشست دریافت می‌شوند و با خروج کامل/Refresh پاک می‌شوند.

## رفتار رابط

- همان کادر «IP یا نام محل»: ابتدا روتر، سپس سوئیچ، منطقه‌ها و ساختمان‌های اداری و محل‌های مجاز از موجودی واقعی.
- تیک مجموعه یا زیرمجموعه، همهٔ اعضای مجاز آن را به لیست می‌آورد؛ انتخاب جزئی، نیمه‌تیک دارد.
- هنگام جست‌وجو، تیک مجموعه فقط اعضای منطبق را انتخاب می‌کند؛ توضیح در درخت نوشته شده است.
- انتخاب گروه به پنج عضو بریده نمی‌شود. لیست‌ها صفحه‌بندی دارند؛ شمارنده، تعداد کامل انتخاب را نشان می‌دهد.
- عملیات فعلیِ بررسی، شرح پورت و تشخیص، فقط روی یک تا پنج سوئیچ در هر نوبت اجرا می‌شوند. با انتخاب روتر/نوع دیگر یا تعداد بیشتر، توضیح روشن و دکمه‌های غیرفعال نمایش داده می‌شود؛ کنترلر قبل از API هم کنترل دارد.
- رفتارهای عملیاتی قبلی: پورت‌های دقیق مثل ۶ و ۱۰، تأیید جداگانهٔ تغییر، بررسی MAC قبلی در همان سوئیچ، حفظ IP مستقل هر پورت و بخش تشخیص فقط‌خواندنی اختیاری حفظ شده‌اند. انتخاب همهٔ روترها به معنی اضافه‌شدن فرمان پیکربندی/رفع روتر نیست.

## آزمون و حدود پذیرش

آزمون‌های رابط و کنترلر شامل ۴۳ مورد، انتخاب گروه ۴۰۰۰ عضوی، کیبورد، جلوگیری از ارسال درخواست سوئیچ برای روتر، و عرض‌های ۳۹۰/۷۶۸/۱۴۴۰ هستند. کنترل انتشار با `scripts/verify_server_fix_release.py` هش، manifest، تطابق هر ۲۳ فایل با سورس و اجرای تست‌های backend از فایل‌های استخراج‌شده را بررسی می‌کند. این بررسی روی Linux و با fixture/mock است، نه پذیرش نصب PowerShell روی Windows/IIS یا اتصال به دستگاه واقعی. پیش از استفادهٔ عملیاتی، پذیرش محیط تست ویندوز لازم است.

## ارزیابی کانتینر

کانتینری‌کردن سرویس مرکزی مناسب است، اما ZIP حاضر Docker image نیست و Dockerfile جدیدی در این انتشار ساخته نشده است.

پیشنهاد: یک کانتینر Linux غیر root برای Python/Waitress و رابط احرازشده، پشت reverse proxy با HTTPS و همان origin. SQLite و نسخه‌های پشتیبان روی volume خصوصی و قابل‌بکاپ باشند؛ known_hosts تأییدشده read-only mount شود؛ مسیر موقت SSH روی tmpfs خصوصی باشد. رمز تجهیزات در image، Compose، فایل env یا volume ذخیره نشود؛ فقط گذرای حافظهٔ درخواست/فرزند SSH بماند. دسترسی خروجی به شبکهٔ مدیریت و SSH اهداف لازم است؛ privileged یا host networking پیش‌فرض لازم نیست.

**مانع فعلی عملیات واقعی SSH:** در `server/equipment_probe.py`، `prepare_askpass()` یک `askpass.exe` بدون رمز را با `csc.exe` از .NET Framework ویندوز می‌سازد. با اینکه مسیر انتخاب `ssh` غیر ویندوز هم وجود دارد، این helper فعلی در Linux بدون تغییر اجرا نمی‌شود. پیش‌فرض مسیر Python فرزند هم ویندوزی است و باید در تنظیمات کانتینر اصلاح شود. صرفاً نوشتن Dockerfile به معنی آماده‌شدن SSH نیست.

برای Linux، ASKPASS بدون فایلِ حامل رمز باید پورت و تست شود؛ تمام محدودیت‌های strict host key، فرمان‌های ثابت، timeout، CSRF/Origin و permission/scope پابرجا بمانند. تا تکمیل این پذیرش، عملیات SSH کانتینری باید خاموش بماند. جایگزین، Windows container است که به تطابق نسخهٔ میزبان/ایمیج، OpenSSH و پیش‌نیاز .NET Framework نیاز دارد و سنگین‌تر است.

در گام اول یک instance/یک فرایند برنامه روی volume محلی توصیه می‌شود؛ چند replica بدون طراحی قفل‌های بین‌فرایندی عملیات، هماهنگی ticketها و دیتابیس امن نیست. SQLite روی share شبکه‌ای یا volume مشترک چند میزبان توصیه نمی‌شود. برای ارتقا، قبل از تغییر image بکاپ SQLite سازگار گرفته شود؛ rollback image به معنی rollback امن schema/data نیست.
