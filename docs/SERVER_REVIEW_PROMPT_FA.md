# پرامپت یکسان برای بررسی مستقل FAM SERVER

متن زیر را همراه فایل ZIP کامل، بدون گزارش دو بررسی‌کنندهٔ دیگر، برای هر نفر بفرستید. جای خالی انتهای متن فقط شناسهٔ بررسی‌کننده است.

---

نقش تو: بازبین مستقل ارشد Python/Flask، امنیت برنامهٔ وب و اتوماسیون شبکه. فایل پیوست، سورس FAM SERVER و اجزای وابسته است. فعلاً فقط بررسی و گزارش کن؛ بدون اجازه فایل‌ها را تغییر نده، چیزی نصب/مستقر نکن و به هیچ تجهیز یا سرویس واقعی وصل نشو. برای این بررسی رمز یا اطلاعات محیط واقعی درخواست نکن.

## هدف و روش

می‌خواهم اشکالات واقعی، ریسک‌های عملیاتی و پیشنهادهای قابل اجرا را بشناسم؛ نه تأیید کلی کد یا فهرست توصیه‌های عمومی. از README_REVIEW_FA.md و SOURCE_REVISION.txt شروع کن. ادعاهای README و کامنت‌ها را تضمین صحت ندان؛ با مسیر اجرای واقعی کد تطبیق بده. نام متغیر، وجود یک تابع اعتبارسنجی یا سبز بودن تست به‌تنهایی اثبات اعمال حفاظت در همهٔ endpointها نیست.

ابتدا فایل‌های در دسترس و محدودیت بررسی را مشخص کن. اگر فایل ZIP را واقعاً نمی‌توانی بخوانی یا ابزار اجرای تست نداری، صریح بگو؛ ادعای خواندن کل پروژه، اجرای تست، امنیت کامل یا کارکرد روی Windows/تجهیز واقعی نکن. هر بخش بررسی‌نشده را «بررسی‌نشده» ثبت کن، نه سالم.

## محدودهٔ اصلی

1. server/app.py، نشست و login، احراز هویت، مجوزهای عملیات، محدودهٔ داده و اعتبارسنجی API؛ همچنین server/equipment_inventory.py، server/equipment_ops.py، server/equipment_probe.py و server/manage.py.
2. src/shared-access.js، src/shared-sync.js، src/equipment-live-server.js، inventory/store، Excel import/export، و UI ساخته‌شده در server/private_ui/FAM.html. مسیر مرورگر → API → helper → دستگاه → پاسخ مرورگر را دنبال کن؛ فقط تابع SSH را جداگانه بررسی نکن.
3. server/www، Windows/IIS، اسکریپت‌های نصب/به‌روزرسانی، بکاپ/بازیابی، dependency pinها، تست‌ها و مستندات مرتبط. پچ فعلی SERVER را با سورس مقایسه کن. نبود باینری نصب یا artifact تاریخی در این بستهٔ سورس را از باگ برنامه جدا کن.
4. exports/equipment-ansible را جداگانه و با برچسب «نسخهٔ مستقل Ansible، نه بخش مستقر FAM» بررسی کن. نبود نشست/مجوزهای وب در آن را با API FAM اشتباه نگیر؛ مرز اعتماد کنترلر، اجرای واقعی module/pluginها و احتمال bypass یا نشت داده را بررسی کن.

## موارد حساس که باید از روی کد راستی‌آزمایی شوند

- احراز هویت و ابطال نشست؛ Origin/CSRF، cookie، کنترل عملیات و ترکیب محدوده‌های type/model/region/siteKind/site. دسترسی مستقیم به endpoint، IP خارج از inventory و کاربر محدود را بررسی کن.
- اعتبارسنجی IPv4 و interface در تمام لایه‌ها، تزریق فرمان/argument، SSRF و تطبیق مقادیر بین مرورگر، API و helper. محدودهٔ موردنیاز RFC1918 و RFC6598 یعنی 100.64.0.0/10 است؛ نه تمام 100/8 و نه اینترنت عمومی.
- رمز/نام کاربری در argv، URL، env، stdin، exception، لاگ، DB، فایل موقت، خروجی CLI و مرورگر؛ طول عمر RAM، خروج/refresh و پاک‌سازی منابع در success/error/timeout. env فرزند و حافظهٔ پردازش را نیز در مدل تهدید کنترلر بررسی کن، نه اینکه وجود env را خودبه‌خود مساوی فایل دائمی بدانی.
- اعتماد به host key؛ crypto allowlist و استثنای محدود aes128-cbc. هر fallback یا option که عملاً اعمال نمی‌شود را با دلیل مشخص کن.
- تشخیص err-disabled در جدول واقعی، جدول ناقص/تکراری/صفحه‌بندی‌شده، خطای احراز هویت و connection failure؛ هیچ‌کدام نباید نتیجهٔ clean بسازند. disabled با err-disabled یکی نیست.
- تأیید دقیق مقصد و پورت، اتصال ticket به کاربر/مقصد/نام کاربری/پورت/زمان، replay و هم‌زمانی، بررسی تازهٔ پیش از تغییر و بررسی همان پورت پس از تغییر. عدم امکان دست‌کاری یا عبور از ترتیب را بررسی کن.
- محدودیت تعداد، اجرای سریالی، timeoutهای هماهنگ، نتیجهٔ نامشخص پس از قطع ارتباط و خطر تکرار عملیات. خروج موفق SSH یا ارسال no shutdown را بدون بررسی بعدی معادل رفع قطعی ندان. ریشهٔ خطا ممکن است باقی بماند.
- ممنوعیت Enable، فرمان آزاد، تغییر خارج از پورت تأییدشده و write memory/copy running-config/config-save در مسیر رفع. ویرایشگر آفلاین کانفیگ نباید مسیر اجرای آزاد روی دستگاه ایجاد کند.
- استثنای خروجی CLI فقط مسیر درخواستی show int des است: محدود، پالایش‌شده، scoped و نمایش با textContent؛ نه بنر، prompt، secret یا خطای داخلی.
- SQLite، revision/epoch، تداخل نوشتن، rollback، idempotency، audit، import/export Excel، وابستگی دسته‌ها، XSS و formula injection؛ حفظ داده و مجوزها هنگام مهاجرت و به‌روزرسانی.
- مرز خصوصی IIS: DB، بکاپ، کد backend، تنظیمات حساس و UI محافظت‌شده نباید ناخواسته عمومی شوند. default/bootstrap accountهای موجود در سورس را از credential واقعی جدا و ریسک راه‌اندازی را مستقل بررسی کن.
- برای Ansible: شکل واقعی آرگومان‌های ios_command/ios_config، loader افزونه‌ها، discovery پنهان، no_log/callback، host-key config، cipher enforcement، pre/post-check و اجرای مرتب هر دو فرمان را بررسی کن؛ تست mock را با اثبات رفتار transport واقعی یکی ندان.

این‌ها نیازمندی‌اند، نه ادعای اینکه همگی درست پیاده شده‌اند. اگر نقضی دیدی گزارش کن. برای رفع مشکل پیشنهاد خاموش کردن host-key checking، گسترش IP به همهٔ مقصدها، ذخیرهٔ رمز، ضعیف کردن cipherها، افزودن Enable/ذخیرهٔ کانفیگ یا دور زدن scopeها نده. اگر قیدی مانع اجرای امن است، همان تعارض و گزینهٔ امن جایگزین را توضیح بده.

## تست و شواهد

در صورت داشتن ابزار، فقط در محیط ایزوله و با دادهٔ ساختگی، DB موقت و SSH mock تست کن. نصب روی سرور، تماس با switch، اجرای installer مدیریتی و تغییر دادهٔ واقعی مجاز نیست. فایل‌های setup، dependency manager و build script را پیش از اجرا بخوان. برای هر تست نام/فرمان، محیط، نتیجه و موارد پوشش‌نداده را ثبت کن. تست‌های missing artifact یا dependency را از شکست assertion کد تفکیک کن. برای یک bug، نمونهٔ بازتولید حداقلی یا تست regression امن پیشنهاد بده؛ نه payload برای تجهیز واقعی.

## قالب پاسخ الزامی

A. خلاصهٔ مدیریتی کوتاه و وضعیت «آماده / آماده با شرط / فعلاً نامناسب» با دامنهٔ دقیق همین قضاوت؛ بدون درصد اطمینان ساختگی.

B. فهرست فایل‌های واقعاً بررسی‌شده، تست‌های واقعاً اجراشده و بخش‌های بررسی‌نشده.

C. جدول یافته‌ها با ستون‌های:
ID | شدت Critical/High/Medium/Low/Info | اطمینان High/Medium/Low | وضعیت تأییدشده/محتمل/نیازمند تست | مسیر فایل و شمارهٔ خط/نام تابع | شواهد/مسیر اجرا | پیش‌شرط و اثر | پیشنهاد حداقلی | تست regression.

هر یافته باید مشخص و قابل پیگیری باشد. اگر line number دقیق نداری، جعل نکن و نام تابع و قطعهٔ کوتاه کد بده. یافتهٔ تأییدشده، فرضیه و پیشنهاد نگهداشت را قاطی نکن؛ یافته‌های تکراری را ادغام کن. نبود یک حفاظت در تابعی که upstream الزاماً آن را اعمال می‌کند را بدون دنبال‌کردن call chain باگ اعلام نکن.

D. پنج اصلاح مهم به ترتیب اولویت، با ریسک تغییر و اثر احتمالی روی رفتار/داده/مجوزها. فعلاً patch اعمال نکن؛ اگر نمونهٔ diff می‌دهی آن را صرفاً پیشنهادی علامت بزن.

E. سؤالات باز و تست‌هایی که فقط روی Windows/IIS، RADIUS یا آزمایشگاه مجاز تجهیزات می‌توان نتیجه‌شان را مشخص کرد.

اگر ایراد تأییدشده پیدا نکردی، همان را بگو و محدودیت بررسی را ذکر کن؛ برای پر کردن گزارش ایراد نساز. گزارش دو بازبین دیگر را ندارید؛ مستقل نتیجه بدهید.
