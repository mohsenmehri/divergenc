# فام مرکزی — نسخهٔ آزمایشی پنج‌کاربره برای IIS

> **نصب خودکار برای سرور 10.16.243.18 و آدرس https://ertebatat-fam:** ابتدا [این راهنما](AUTO_INSTALL_FAM_FA.md) و فایل `INSTALL-FAM.cmd` را ببینید. ادامهٔ این سند روش دستی است.

مبنا **نسخهٔ اصلی دوتمی** است، نه Nexus/Workspace. تم ۲ همان ترتیب اجزا، اندازه‌ها، فرم‌ها و ساختار تم ۱ را دارد؛ فقط پالت روشن آن حفظ شده است. فایل‌های مستقل قبلی تغییر نکرده‌اند.

## کدام فایل را نصب کنم؟

- **بستهٔ مرکزی:** [FAM-Central-IIS.zip](../releases/FAM-Central-IIS.zip) — HTML، سرویس Python، تنظیم IIS، اسکریپت راه‌اندازی و ابزار پشتیبان.
- **صفحهٔ مرکزی:** [server/www/FAM.html](../server/www/FAM.html). این فایل به‌تنهایی برنامهٔ مرکزی نیست؛ API هم باید اجرا شود.
- **FAM.html ریشهٔ مخزن:** نسخهٔ مستقل و مرورگرمحلی، با اصلاح ظاهر تم ۲؛ آن را به جای صفحهٔ مرکزی نصب نکنید.

مرجع اطلاعات مرکزی **`C:\FAMData\fam.sqlite3` روی دیسک سرور** است. پس از نصب، پنج کاربر فقط نشانی HTTPS سایت را در مرورگر خود باز می‌کنند؛ RDP، اشتراک پوشه و نصب Python روی رایانهٔ کاربران لازم نیست. فایل HTML و فایل XLSM اصلی با هر ویرایش بازنویسی نمی‌شوند. XLSM اصلی دست‌نخورده مانده است؛ برای Excel از خروجی برنامه استفاده کنید.

## رفتار نسخه

- حساب‌ها و مجوزها روی سرور هستند. تغییر نام/نقش/رمز یا غیرفعال‌کردن حساب، نشست‌های قدیمی آن حساب را باطل می‌کند؛ نشست جاریِ مجاز در تغییر رمز خود کاربر حفظ می‌شود.
- نقش ۱: همهٔ امکانات؛ نقش ۲: همه به جز مدیریت کاربران و ابزار کد؛ نقش ۳: مشاهده/جستجو/درج/حذف، بدون ویرایش مستقیم و تنظیمات؛ نقش ۴: فقط شیت‌های صریحاً مجاز و، برای استان‌ها، منطقهٔ مجاز. دادهٔ خارج از مجوز نقش ۴ حتی در پاسخ API ارسال نمی‌شود.
- مخفی‌کردن واقعی View Source/DevTools مرورگر ممکن نیست. امنیت داده به کنترل‌های سرور وابسته است، نه پنهان‌بودن دکمه‌ها. ابزار داخل برنامهٔ کد فقط برای سطح ۱ است.
- پیام ثبت قطعی فقط بعد از تأیید تراکنش سرور نمایش داده می‌شود. تا آن زمان تغییر بعدی موقتاً متوقف است.
- هر ثبت یک شمارهٔ نسخه دارد. اگر دو مرورگر نسخهٔ قدیمی یکسان داشته باشند، اولین ثبت پذیرفته و ثبت بعدی با تعارض رد می‌شود؛ **حتی اگر روی دو شیت متفاوت باشد**. ادغام خودکار یا «آخرین نویسنده برنده است» وجود ندارد.
- مرورگرهای فعال حدود هر دو ثانیه وجود نسخهٔ جدید را بررسی می‌کنند. اعمال دادهٔ جدید هنگام تایپ، ویرایش سلول یا بازبودن پنجرهٔ عملیات عقب می‌افتد تا کار جاری از بین نرود؛ پس از پایان کار/خروج از ورودی، خودکار تازه می‌شود. تب پس‌زمینه هنگام بازگشت تازه می‌شود.
- در قطع ارتباط، «ذخیره شد» نمایش داده نمی‌شود. صفحهٔ خطا نسخهٔ کاری را در حافظه نگه می‌دارد. تلاش دوباره همان شناسهٔ درخواست را می‌فرستد؛ گم‌شدن پاسخ باعث درج تکراری نمی‌شود. مدیرها می‌توانند JSON ثبت‌نشده را دانلود کنند. تعارض نیازمند دریافت نسخهٔ تازه و اعمال مجدد تغییر است؛ بازنویسی اجباری خودکار ندارد.
- **نسخهٔ کاریِ تأییدنشده فقط تا بازبودن صفحه زنده است.** ذخیرهٔ آفلاین کل اطلاعات در مرورگر انجام نمی‌شود. صفحه/مرورگر را در این وضعیت نبندید؛ هشدار خروج هم جای پشتیبان را نمی‌گیرد. نقش ۳ مجوز خروجی کامل ندارد.
- پیش‌نویس‌های دو ورودی جستجو/حذف کوچک و فوری در مرورگر، جدا برای هر حساب، حفظ می‌شوند؛ نوشتن هر حرف باعث فشرده‌سازی کل workbook یا درخواست ثبت روی سرور نمی‌شود. تم و ترجیحات نمایشی شخصی‌اند، نه دادهٔ مشترک. اگر مرورگر اجازهٔ ذخیرهٔ پیش‌نویس ندهد، هشدار نمایش داده می‌شود؛ این حالت را با تأیید ثبت رکورد روی سرور اشتباه نگیرید.
- «برگشت» در نسخهٔ مرکزی **بازگردانی کل آخرین ثبت سرور** است، نه صرفاً آخرین حذف محلی. سطح ۱/۲ پس از دیدن نام ثبت‌کننده و شمارهٔ نسخه و تأیید، می‌تواند آخرین ثبت هر کاربر را برگرداند. اگر در این فاصله کسی ثبت کند، بازگشت نیز با تعارض رد می‌شود. دادهٔ بازگشت از snapshot خود سرور می‌آید؛ بافر ادعایی مرورگر مورد اعتماد نیست.
- «پاک‌سازی» و «بازنشانی» در این نسخه، با تأیید صریح، **دادهٔ مشترک همهٔ کاربران** را تغییر می‌دهند؛ دیگر فقط حافظهٔ یک مرورگر را پاک نمی‌کنند. حساب‌ها و XLSM اصلی باقی می‌مانند و آخرین ثبت قابل برگشت است. قبل از این عملیات پشتیبان بگیرید.
- ورود/خروجی Excel/CSV/JSON، آرشیو حذف، مدیریت دسته‌ها و مناطق حفظ شده‌اند. دادهٔ تاریخی استان‌ها شعبه باقی می‌ماند؛ شیت خودپرداز فقط با درج غیرخالی و تأییدشده ایجاد می‌شود، با عنوان‌ها و ادغام سطر اول استان، بدون انتقال تاریخچه.
- کنترل ساختار ادغام برای نقش ۳ محافظه‌کارانه است. حذف مبهم بین ردیف‌های کاملاً تکراریِ ادغام‌شده ممکن است رد شود؛ در این حالت مدیر باید عملیات را بررسی و انجام دهد، نه اینکه کنترل سرور دور زده شود.

## نصب روی Windows / IIS

این دستورالعمل برای استقرار آزمایشی روی Windows Server دارای IIS، با **Python 3.12 x64**، نوشته شده است. اجرای خودکار PowerShell، گواهی TLS و تنظیم ARR روی Windows واقعیِ شما هنوز آزمایش نشده است؛ پیش از انتقال اطلاعات اصلی، چک‌لیست انتهای راهنما را روی سرور آزمایشی اجرا کنید.

### ۱. پیش‌نیاز و پوشه‌ها

روی **خود سرور** نصب کنید:

1. IIS با Static Content؛ یک سایت اختصاصی فام بسازید.
2. IIS **URL Rewrite 2** و **Application Request Routing 3 (ARR)**؛ نصب IIS به‌تنهایی کافی نیست.
3. Python 3.12 x64 با Python Launcher (`py`) به صورت **Install for all users** در مسیری قابل‌خواندن برای LOCAL SERVICE، نه فقط داخل پروفایل شخصی Administrator. نسخه و وصله‌های امنیتی Python را طبق سیاست سازمان نگه دارید. دسترسی نصب وابستگی‌ها از PyPI یا مخزن تأییدشدهٔ سازمان لازم است. Node/npm برای اجرای بسته لازم نیست.
4. DNS/نشانی پایدار و گواهی HTTPS مورد اعتماد هر پنج مرورگر؛ نشانی مثال را با نشانی واقعی خودتان عوض کنید.

بسته را در `C:\FAM` استخراج کنید؛ ساختار مهم:

```text
C:\FAM\server\app.py
C:\FAM\server\manage.py
C:\FAM\server\requirements.txt
C:\FAM\server\windows\install.ps1
C:\FAM\server\windows\start.ps1
C:\FAM\server\www\FAM.html
C:\FAM\server\www\web.config
C:\FAMData\fam.sqlite3              ← بعد از نخستین اجرای سرویس ساخته می‌شود
```

**فقط `C:\FAM\server\www` ریشهٔ عمومی IIS است.** کل مخزن، پوشهٔ `server`، دیتابیس، لاگ، نسخه‌های پشتیبان و فایل تنظیمات نباید داخل ریشهٔ سایت یا قابل دانلود باشند. دیتابیس باید روی دیسک محلی باشد، نه SMB/NAS، پوشهٔ اشتراکی یا پوشهٔ همگام‌سازی ابری.

### ۲. نصب سرویس پس‌زمینه

PowerShell را با Administrator باز کنید؛ نشانی مثال را عوض کنید:

```powershell
cd C:\FAM
powershell -NoProfile -ExecutionPolicy Bypass -File .\server\windows\install.ps1 `
  -PublicOrigin 'https://fam.example.internal' -DataDir 'C:\FAMData'
```

اسکریپت محیط Python و وابستگی‌های مشخص را نصب می‌کند، تنظیم محلی `windows\settings.json` می‌سازد و وظیفهٔ **FAM-Central** را برای اجرای دائمی در شروع Windows با حساب کم‌اختیار **LOCAL SERVICE** ثبت می‌کند. این وظیفه به لاگین تعاملی یا بازماندن RDP وابسته نیست. در خطا، Task Scheduler تلاش مجدد می‌کند؛ این نسخه Windows Service بومی نیست.

`DataDir` را فقط به یک پوشهٔ **اختصاصی فام** بدهید؛ اسکریپت مجوزهای همان پوشه را محدود می‌کند. بازنصب، دیتابیس یا رمز کاربران موجود را حذف/بازنشانی نمی‌کند. مسیر `DB` را در ارتقا عوض نکنید؛ مسیر اشتباهِ تازه باعث ساخت دیتابیس خالیِ دیگری خواهد شد.

بررسی کنید:

```powershell
Get-ScheduledTask -TaskName FAM-Central
Get-ScheduledTaskInfo -TaskName FAM-Central
Get-NetTCPConnection -LocalPort 8765 -State Listen
Get-Content C:\FAMData\logs\service.log -Tail 60
icacls C:\FAMData /T
```

پورت باید فقط روی **127.0.0.1:8765** گوش کند. پورت ۸۷۶۵ را به شبکه باز نکنید. در پوشهٔ داده، به‌خصوص فایل‌های از قبل موجود، دسترسی صریحِ اضافی برای Everyone/Users نباید باقی مانده باشد. Application Pool و IIS به دیتابیس مجوز Write/Modify نیاز ندارند؛ فقط سرویس بک‌اند آن را می‌نویسد. پوشهٔ برنامه برای LOCAL SERVICE خواندنی و برای کاربران عادی غیرقابل‌ویرایش باشد.

### ۳. تنظیم IIS

1. در IIS Manager، در سطح **Server**، وارد **Application Request Routing Cache → Server Proxy Settings** شوید و **Enable proxy** را فعال کنید.
2. Physical Path سایت فام را دقیقاً `C:\FAM\server\www` بگذارید. برای صفحهٔ ثابت/API مرورگری، Anonymous Authentication سایت فعال باشد؛ احراز هویت برنامه با حساب‌های خودش انجام می‌شود. Application Pool می‌تواند No Managed Code باشد.
3. HTTPS Binding روی ۴۴۳ با Hostname واقعی و گواهی صحیح بسازید. نام Host را محدود کنید. در صورت HTTP Binding روی ۸۰، web.config به HTTPS هدایت می‌کند. نمونهٔ Redirect برای HTTPS استاندارد ۴۴۳ است؛ برای پورت TLS سفارشی مقصد Redirect را متناسب تغییر دهید.
4. `web.config` مسیر `api/*` را از طریق ARR به سرویس loopback می‌فرستد. **Origin و Cookie درخواست را حذف یا بازنویسی نکنید**؛ POST به Origin دقیق تنظیم‌شده وابسته است. API نباید cache شود؛ محدودیت درخواست هر دو لایه ۳۲ MiB است.
5. در فایروال فقط HTTPS مورد نیاز شبکهٔ آزمایشی/VPN را باز کنید. این بسته را بدون سخت‌سازی، سیاست رمز مناسب و بازبینی امنیتی روی اینترنت عمومی نگذارید.
6. از یک رایانهٔ دیگر `https://نام-واقعی-سایت/FAM.html` را **مستقیم در مرورگر** باز کنید، نه file:// و نه HTTP. کوکی ورود HttpOnly/Secure/SameSite=Strict است؛ HTTPS معتبر الزامی است. جاسازی در سایت دیگر/iframe هدف این بسته نیست.

خطای `500.19` معمولاً نیازمند بررسی نصب/قفل پیکربندی URL Rewrite است. `502` معمولاً به اجرا نبودن بک‌اند یا فعال نبودن ARR Proxy مربوط است. اگر صفحه باز می‌شود ولی ورود/ثبت خطای «مبدأ» می‌دهد، Origin نشانی مرورگر را با `PUBLIC_ORIGIN` در `settings.json` مقایسه کنید: scheme، host و port باید دقیقاً یکسان باشند؛ پس از تغییر تنظیم، وظیفه را Stop/Start کنید. پاسخ `401` از GET `/api/session` پیش از ورود طبیعی است.

### ۴. نخستین ورود و انتقال داده

- فقط برای دیتابیس واقعاً تازه، حساب اولیهٔ `admin` با رمز اولیهٔ توافق‌شدهٔ قبلی ساخته می‌شود؛ رمز در رابط یا لاگ چاپ نمی‌شود. **پیش از دسترسی عمومی رمز آن را تغییر دهید** و پنج حساب جداگانه با نقش لازم بسازید. حساب‌های محلی مرورگر به سرور منتقل نمی‌شوند و از روی JSON داده نیز ساخته نمی‌شوند.
- در نسخهٔ قدیمیِ همان مرورگری که دادهٔ درست در آن است، یک **پشتیبان JSON** و ترجیحاً Excel بگیرید. اگر چند مرورگر نسخه‌های متفاوت دارند، آن‌ها را جداگانه نگه دارید و نسخهٔ مرجع را تعیین کنید؛ هیچ انتخاب یا ادغام خودکار امنی وجود ندارد.
- تا پایان انتقال، ویرایش در نسخهٔ قدیمی را متوقف کنید. مدیر پس از ورود به نسخهٔ مرکزی، **یک بار** JSON مرجع یا Excel را با ابزار موجود وارد می‌کند و تأیید ثبت سرور را می‌بیند. اولین مرورگر صرفاً به دلیل ورود، اطلاعات محلی خود را روی سرور منتشر نمی‌کند.
- تعداد شیت‌ها، چند رکورد شعبه/خودپرداز، مناطق، دسته‌ها و آرشیو را مقایسه کنید. سطح ۴ را با حساب جدا امتحان کنید. در نهایت از دیتابیس مرکزی پشتیبان بگیرید و نشانی مرکزی واحد را به پنج نفر بدهید.

## پشتیبان واقعی و بازیابی

JSON/Excel داخل برنامه، خروجی داده است؛ **پشتیبان کامل سرویس نیست** و حساب‌ها/نشست‌ها/همهٔ تاریخچه را شامل نمی‌شود. برای نسخهٔ کامل، ابزار SQLite زیر را با هویت Administrator یا حساب پشتیبان مجاز اجرا کنید:

```powershell
# پشتیبان سازگار از دیتابیس در حال اجرا؛ نام خروجی باید جدید باشد
C:\FAM\server\.venv\Scripts\python.exe C:\FAM\server\manage.py backup `
  --db C:\FAMData\fam.sqlite3 --output C:\FAMData\backups\fam-2026-10-11.sqlite3
```

این ابزار SQLite Backup API و integrity_check را به‌کار می‌گیرد و ابتدا فایل کامل را می‌سازد. از کپی عادی `fam.sqlite3` هنگام اجرای سرویس استفاده نکنید؛ تغییرات تازه ممکن است در فایل WAL باشند. زمان‌بندی روزانهٔ پشتیبان را در Task Scheduler سازمان تنظیم و حداقل یک نسخهٔ رمزگذاری‌شدهٔ خارج از دیسک سرور نگه دارید. آن پوشه هم دادهٔ حساس و هش رمزها دارد؛ به کاربران سایت دسترسی ندهید. چرخهٔ نگهداری/پاک‌سازی پشتیبان‌ها خودکار نشده است.

برای بازگردانی، **همهٔ پردازش‌های بک‌اند را متوقف** کنید؛ IIS را نیز موقتاً از دسترس کاربران خارج کنید. ابزار نمی‌تواند توقف سرویس را از روی پرچم تشخیص دهد؛ مسئول اجرا باید آن را واقعاً بررسی کند:

```powershell
Stop-ScheduledTask -TaskName FAM-Central
Get-NetTCPConnection -LocalPort 8765 -State Listen -ErrorAction SilentlyContinue
# دستور بالا نباید listener نشان دهد؛ در غیر این صورت ادامه ندهید.
C:\FAM\server\.venv\Scripts\python.exe C:\FAM\server\manage.py restore `
  --input C:\FAMData\backups\fam-2026-10-11.sqlite3 --db C:\FAMData\fam.sqlite3 --server-stopped
Start-ScheduledTask -TaskName FAM-Central
```

قبل از جایگزینی، ابزار یک فایل `before-restore` از وضعیت جاری می‌سازد. بازیابی از مسیر SQLite انجام می‌شود، نه تعویض نادرست فایل زیر WAL. شناسهٔ دورهٔ داده عوض و نشست‌ها/رسیدهای درخواست قبلی باطل می‌شوند؛ همه دوباره وارد شوند. **حساب‌ها و رمزها نیز به زمان پشتیبان برمی‌گردند.** بازیابی باید نخست روی نسخهٔ آزمایشی تمرین شود.

ثبت وقایع روی سرور انجام می‌شود. نمای داخلی ۲۰۰ ثبت اخیر را نشان می‌دهد؛ فرادادهٔ تاریخچه در دیتابیس باقی می‌ماند. snapshot کاملِ پیش از ۵۰ ثبت اخیر نگه داشته می‌شود؛ این‌ها جای پشتیبان زمان‌بندی‌شده و خارج از سرور را نمی‌گیرند. دکمهٔ برگشت فقط آخرین ثبت را هدف می‌گیرد. دسترسی/نگهداری لاگ خصوصی سرویس و پاک‌سازی دوره‌ای آن با مدیر سرور است.

## ارتقا

ابتدا Backup API، سپس توقف FAM-Central؛ فایل‌های برنامه و `www` را جایگزین کنید، اما **دیتابیس، settings.json و پشتیبان‌ها را نگه دارید**. با همان DB/PUBLIC_ORIGIN شروع کنید. کاربران صفحه را تازه کنند. پوشهٔ داده عمداً بیرون از بسته است؛ ZIP هرگز دادهٔ آزمایشی، هش کاربران یا دیتابیس زنده ندارد.

گزارش دقیق آزمون‌های این انتشار: [SHARED_TEST_REPORT.md](SHARED_TEST_REPORT.md).

## آزمون‌ها و محدودیت ادعا

آزمون‌ها روی Linux، Flask/SQLite و Chromium واقعی اجرا می‌شوند؛ این به معنی تأیید نصب Windows/IIS یا تضمین کارایی برای دادهٔ واقعی شما نیست. بسته برای آزمایش پنج‌کاربره تهیه شده، نه اتوماسیون ۶۰۰ روتر. سقف API برابر ۳۲ MiB برای هر درخواست است؛ این نسخه در هر ثبت snapshot کامل داده را می‌فرستد، نه تغییرات سطری. فایل بسیار بزرگ، پنج ثبت واقعاً همزمان و شرایط شبکهٔ سازمان را جدا اندازه بگیرید.

چک‌لیست پذیرش روی IIS واقعی:

- ورود پنج حساب در پنج مرورگر/رایانه؛ درج، ویرایش سطح ۱/۲، حذف و مشاهدهٔ خودکار در بقیه.
- رد ثبت همزمانِ قدیمی؛ ثبت‌نشده بودن عملیات در قطع شبکه؛ موفقیت تلاش دوباره بدون رکورد تکراری.
- رد ویرایش مستقیم سطح ۳، رد همهٔ تغییرات سطح ۴ و نبود دادهٔ غیرمجاز در Network/API آن حساب.
- تغییر رمز خود کاربر و عدم امکان تغییر مشخصات/نقش توسط غیرمدیر؛ عدم بازنشانی رمز بعد از Restart.
- آرشیو حذف، برگشت آخرین ثبت توسط مدیر، خروجی‌ها و انتقال شعبه/خودپرداز بدون جابه‌جایی تاریخچه.
- Restart سرویس و Windows؛ حفظ داده؛ نیاز نداشتن به بازماندن نشست RDP.
- پشتیبان و بازیابی روی دیتابیس آزمایشی؛ تأیید خصوصی بودن `.sqlite3`، فایل WAL، لاگ و تنظیمات از بیرون سایت.
- یکسان‌بودن ساختار دو تم روی نمایشگرهای واقعی کاربران؛ فقط پالت فرق کند.

برای اجرای تست توسعه، از ریشهٔ مخزن:

```sh
python -m venv .venv
.venv/bin/pip install -r server/requirements.txt
.venv/bin/python -m unittest discover -s server/tests -v
python scripts/embed_ui_themes.py
python scripts/build_shared.py
npm ci
# سرور آزمایشی را طبق server/tests/serve_browser.py جدا راه بیندازید:
FAM_SHARED_TEST_URL=http://127.0.0.1:8765/FAM.html node scripts/smoke_shared.cjs
```

**اسکریپت مرورگر، دادهٔ ساختگی وارد و حساب‌های آزمایشی می‌سازد؛ هرگز URL واقعی/دیتابیس عملیاتی را به آن ندهید.** ابزارهای تست جزئی از مسیر اجرای سایت نیستند.
