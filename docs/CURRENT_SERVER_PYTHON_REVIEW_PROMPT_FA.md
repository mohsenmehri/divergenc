# پرامپت بررسی مستقل نسخهٔ فعلی SERVER — تمرکز بر Python تجهیزات

این متن را همراه همین بسته به هر سه بازبین بدهید. فقط شناسهٔ انتهای متن را A، B یا C قرار دهید؛ نظر دو نفر دیگر را پیش از پایان بررسی مستقل در اختیارشان نگذارید.

---

نقش تو بازبین مستقل ارشد Python/Flask، امنیت وب و اتصال SSH به تجهیزات Cisco IOS است. فایل پیوست، سورس نسخهٔ فعلی SERVER پروژه و پچ فعلی آن است؛ این بسته از روی یک سرور عملیاتی دریافت نشده و تطبیق آن با نصب واقعی هنوز تأیید نشده است.

## اولویت اصلی من

بیشتر از همه می‌خواهم **کدهای پایتون اتصال به تجهیزات، بررسی خطا و رفع پورت** عمیق و خط‌به‌خط بررسی شوند. بررسی کلی سایر بخش‌های سرور نیز الزامی است، اما نباید جای بررسی دقیق مسیر SSH را بگیرد.

ترتیب بررسی:

1. `server/equipment_probe.py`: حمل‌ونقل Windows OpenSSH، اعتبارسنجی ورودی، اجرای فرمان‌های ثابت، ASKPASS، parser، pre-check/write/post-check و cleanup.
2. `server/equipment_ops.py`: API اتصال، مجوز مقصد و عملیات، اعتبارسنجی، محدودیت اجرا و ticket تأیید پورت.
3. `server/equipment_inventory.py` و اتصال این ماژول‌ها به `server/app.py`: موجودی، محدوده‌های مجاز کاربر و اعمال سمت سرور.
4. `src/equipment-live-server.js`: دنبال‌کردن مسیر کامل مرورگر → API → helper → SSH → خروجی، تأیید اپراتور و نمایش نتیجه.
5. سپس بررسی کامل سایر مسیرهای `server/app.py`، `server/manage.py`، `src/shared-access.js`، `src/shared-sync.js`، Excel/import/export، UI نهایی، SQLite، اسکریپت‌های Windows/IIS، backup/restore و پچ فعلی SERVER.

## سؤالات اصلی اتصال و رفع خطا

- آیا حساب محدود با فراخوانی مستقیم endpoint یا IP دستی می‌تواند از مجوز عملیات یا محدوده‌های type/model/region/siteKind/site عبور کند؟ اعمال حفاظت را در call chain واقعی بررسی کن؛ صرف وجود تابع کافی نیست.
- آیا host/interface/username/password در تمام لایه‌ها به‌درستی اعتبارسنجی می‌شوند؟ امکان command/argument injection، SSRF یا هدف‌گیری خارج از محدوده وجود دارد؟ رنج‌های موردنیاز RFC1918 و `100.64.0.0/10` هستند، نه تمام 100/8 یا اینترنت عمومی.
- آیا credential در argv، URL، DB، فایل موقت، exception، خروجی، log یا حافظهٔ ماندگار مرورگر نشت می‌کند؟ نحوهٔ stdin/env فرزند و ASKPASS را با مدل تهدید واقعی پردازش بررسی کن؛ env را خودبه‌خود معادل فایل دائمی ندان. سناریوهای موفقیت، خطا، timeout، logout و refresh را پوشش بده.
- آیا host key واقعاً بررسی می‌شود؟ cipher allowlist و استثنای محدود `aes128-cbc` واقعاً در اجرای SSH اعمال می‌شوند؟ fallback ناامن یا گزینهٔ بی‌اثر وجود دارد؟
- آیا parser، err-disabled را از disabled/notconnect جدا می‌کند؟ جدول ناقص، تکراری، صفحه‌بندی‌شده، خطای ورود، بنر، نبود پورت یا پاسخ ناشناخته نباید نتیجهٔ clean بسازند.
- آیا تأیید دقیق مقصد و پورت و اتصال ticket به کاربر/host/username/interface/زمان درست است؟ replay، دست‌کاری، اجرای هم‌زمان و تغییر وضعیت بین check و recover را بررسی کن.
- آیا بلافاصله پیش از تغییر، وجود و وضعیت همان پورت دوباره بررسی می‌شود؟ فقط همان interface با shutdown/no shutdown تغییر می‌کند؟ آیا پس از تغییر، جدول معتبر و همان پورت دوباره بررسی می‌شود؟ ارسال موفق فرمان یا خروج موفق SSH به‌تنهایی موفقیت نیست.
- آیا Enable، فرمان آزاد، تغییر خارج از پورت تأییدشده یا ذخیرهٔ کانفیگ قابل اجراست؟ ویرایشگر آفلاین نباید مسیر اجرای آزاد روی دستگاه بسازد.
- آیا سقف تعداد، اجرای سریالی، timeoutها، خطای نیمه‌کاره و cleanup فرایند/فایل موقت هماهنگ‌اند؟ پس از قطع ارتباط، وضعیت نامشخص یا احتمال اجرای فرمان قبلی چگونه گزارش می‌شود و آیا retry می‌تواند مضر باشد؟
- خروجی خام CLI فقط برای مسیر درخواستی `show int des` است؛ پالایش، محدودیت اندازه، scope و نمایش با textContent را بررسی کن. هیچ بنر، prompt، secret یا خطای داخلی نباید از این مسیر عبور کند.
- cycle پورت علت ریشه‌ای BPDU Guard/Port Security/UDLD و مانند آن را لزوماً رفع نمی‌کند. ادعای موفقیت و احتمال بازگشت err-disabled را با معنای واقعی نتیجه تطبیق بده.

## بررسی بقیهٔ برنامه

احراز هویت، bootstrap/default account، ابطال نشست، cookie، CSRF/Origin، مجوزها و scopeها، XSS، formula injection و import/export، validation، تداخل نوشتن/revision/idempotency، transaction و rollback، audit، backup/restore، مهاجرت بدون حذف داده و مرز عمومی/خصوصی IIS را بررسی کن. DB، backup، backend، تنظیمات حساس و UI محافظت‌شده نباید ناخواسته عمومی شوند. payload پچ را با سورس فعلی مقایسه کن. مستندات و کامنت‌ها را ادعای نیازمند راستی‌آزمایی بدان، نه تضمین صحت.

## محدودیت و روش

فعلاً فقط بررسی و گزارش کن؛ فایل‌ها را تغییر نده و patch اعمال نکن. به تجهیز یا سرویس واقعی وصل نشو، installer اجرا نکن، DB واقعی را دست‌کاری نکن و اطلاعات ورود نخواه. اگر ابزار داری، فقط پس از خواندن تست‌ها، در محیط ایزوله با دادهٔ ساختگی، DB موقت و SSH mock تست کن. تست موفق mock را اثبات عملکرد Windows/IIS، RADIUS یا سخت‌افزار ندان.

برای رفع مشکل، خاموش‌کردن host-key checking، ذخیرهٔ رمز، بازکردن همهٔ IPها، ضعیف‌کردن cipherها، دورزدن scopeها یا افزودن Enable/config-save پیشنهاد نده. اگر قیدی با کارکرد امن تعارض دارد، همان تعارض و گزینهٔ امن را گزارش کن.

اگر ZIP را نمی‌توانی بخوانی یا امکان اجرای تست نداری، صریح بگو. شمارهٔ خط، نتیجهٔ تست یا پوشش خواندن را جعل نکن. نبود artifact تاریخی یا dependency را از باگ runtime جدا کن. «بررسی‌نشده» با «سالم» فرق دارد.

## قالب گزارش

A. خلاصهٔ کوتاه و ارزیابی آمادگی، با دامنه و محدودیت دقیق.

B. **گزارش اختصاصی Python تجهیزات**: فایل‌ها/توابع واقعاً خوانده‌شده، مسیر اجرای اتصال و رفع، نقاط درست، اشکالات و موارد نیازمند آزمایش Windows/تجهیز واقعی. این قسمت نباید صرفاً چند توصیهٔ عمومی باشد.

C. جدول یافته‌ها:
`ID | بخش | شدت Critical/High/Medium/Low/Info | اطمینان | تأییدشده/محتمل/نیازمند تست | فایل و خط یا تابع | شواهد و شرایط وقوع | اثر | اصلاح حداقلی | تست regression امن`

D. گزارش سایر بخش‌های SERVER با همین استاندارد شواهد؛ پیشنهاد نگهداشت را با آسیب‌پذیری اثبات‌شده یکی نکن و یافته‌های تکراری را ادغام کن.

E. تست‌های واقعاً اجراشده با فرمان و نتیجه، تست‌های اجرا‌نشده و علت آن‌ها، و فایل‌های بررسی‌نشده.

F. پنج اصلاح اولویت‌دار با ریسک تغییر و اثر احتمالی روی داده/مجوز/رفتار موجود؛ هنوز هیچ تغییر خودکاری اعمال نکن.

اگر ایراد تأییدشده پیدا نکردی، همان را با محدودیت بررسی بگو؛ برای پرکردن گزارش ایراد نساز. یافتهٔ تابعی را که upstream به‌طور الزامی محافظت می‌شود بدون بررسی call chain آسیب‌پذیری اعلام نکن.
