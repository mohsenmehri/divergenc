# داوری مستقل هر سه گزارش — Python تجهیزات و SERVER

تاریخ: ۲۰۲۶-۱۰-۱۷
مرجع بررسی: سورس پروژه در `59d7a4f` و بستهٔ `FAM-SERVER-Current-Python-Review.zip`. این داوری، تطبیق با سرور عملیاتی نیست.
شناسه‌ها در این سند: **R1 = نفر اول، R2 = نفر دوم و فایل GitHub او، R3 = نفر سوم**؛ چون خود گزارش‌ها همگی از A یا A/B/C استفاده کرده‌اند.

**هیچ اصلاحی در کد اجرایی برنامه، تنظیمات استقرار یا releaseها اعمال نشده است.** فقط این گزارش و اسکریپت بازتولید تشخیصی اضافه شده‌اند. هیچ رمز واقعی دریافت نشد، هیچ تجهیز واقعی تماس گرفته نشد و هیچ DB عملیاتی تغییر نکرد.

## ۱. نتیجهٔ اصلی

چند ایراد واقعی وجود دارد و آن‌ها را می‌پذیرم: رمز bootstrap شناخته‌شده در نصب تازه، ticket قابل استفادهٔ مجدد، نبود قفل recovery سمت سرور، ناسازگاری backup با مدیر سفارشی و ناهماهنگی masking اطلاعات حساس. خطر قطع ارتباط در میانهٔ cycle پورت هم واقعی و مهم است، اما نباید آن را به ادعای «در هر timeout پورت حتماً خاموش می‌ماند» تبدیل کرد.

در مقابل، «پرامپت خالی»، «تست Connector خراب در کل مخزن»، «باید فوراً کلید ticket را دائمی کرد» و «رد جدول کوتاه یعنی clean اشتباه» نتیجه‌گیری‌های درستی دربارهٔ runtime فعلی نیستند. اصلاح کورکورانهٔ quote مسیر known_hosts، فعال‌کردن همهٔ پورت‌های disabled، اعتماد مستقیم به X-Forwarded-For یا افزودن apostrophe به رشته‌های سالم XLSX نیز توصیه نمی‌شود.

۹۶ تست قبلی موفق‌اند، ولی این موضوع نبودِ ایراد امنیتی/عملیاتی را اثبات نمی‌کند. برای recovery بی‌نظارت یا هم‌زمان، پیش از اصلاح موارد اولویت‌دار و تست مجاز Windows/IOS تأیید انتشار نمی‌دهم. وضعیت read-only هم فقط پس از تأیید محیط و اعتماد host key قابل ارزیابی است، نه با mock به‌تنهایی.

## ۳. یافته‌های مهم و حکم نهایی

### F-01 — رمز ثابت bootstrap: تأیید، اهمیت بالا در نصب fresh

ارجاع: R1 BUG-07، R2 S2، R3 A-01.
کد: `server/app.py:541–548`؛ اسکریپت‌های startup/نصب.

اگر `FAM_INITIAL_PASSWORD` نباشد، DB تازه با admin و رمز ثابت شناخته‌شده ساخته می‌شود. با TESTING=False و DB موقت نیز login موفق بازتولید شد. این فقط یک ایراد مستندسازی کم‌خطر نیست؛ در نصب شبکه‌ای تازه، تا وقتی رمز عوض نشده، ریسک تصاحب حساب مدیر وجود دارد.

این ادعا **به معنی آن نیست که رمز نصب فعلی کاربر هنوز پیش‌فرض است**؛ فایل DB یا رمز واقعی نصب را ندیده‌ایم. حذف fallback نیز نباید DB یا رمز کاربران موجود را reset کند. مسیر مناسب: راه‌اندازی تازه با bootstrap امن و صریح، بدون رمز در argv/log یا فایل plaintext؛ حساب‌های موجود دست‌نخورده بمانند. افزودن پارامتر plaintext خط فرمان یا صرفاً یک هشدار در README کافی نیست.

### F-02 — قطع ارتباط وسط cycle: خطر عملیاتی تأییدشده، اجرای واقعی جزئی نیازمند آزمایشگاه

ارجاع: R2 E1.
کد: `equipment_probe.py:525–554`، `equipment_ops.py:221–233`، `equipment-live-server.js:83`.

cycle یک تراکنش اتمی روی دستگاه نیست. قطع ارتباط ممکن است پس از shutdown و پیش از اجرای no shutdown رخ دهد. در بازتولید mock، شکست جلسهٔ config موجب خطای عمومی 502 شد و post-check اجرا نشد. درخواست بعدی با جدول disabled، نتیجهٔ not_errdisabled گرفت و هیچ فرمان تغییری نفرستاد.

**تفکیک مهم:** برنامه در این حالت recovered اعلام نمی‌کند؛ UI فعلی هم «نتیجهٔ رفع تأیید نشد» می‌نویسد. not_errdisabled نیز از نظر لفظی نمی‌گوید پورت سالم یا connected است. مشکل واقعی، نبود نتیجه/راهنمای مشخص recovery_uncertain و ناتوانی در تعیین اثر درخواست نیمه‌تمام است. علاوه بر آن، حلقهٔ UI جز در 401/403 برای درخواست‌های بعدی ادامه می‌دهد؛ توقف batch در حالت uncertain انتخاب ایمن‌تری است.

mock ثابت نمی‌کند کدام خط روی IOS اجرا شده؛ این قسمت باید با مجوز در آزمایشگاه بررسی شود. stdin فعلی چند فرمان را یک‌جا می‌فرستد و دریافت/اجرای همهٔ آن‌ها تضمین اتمی ندارد.

**اصلاح خطرناکِ ممنوع:** پس از هر خطا، همهٔ پورت‌های disabled را no shutdown نکنیم. بعضی عمداً غیرفعال‌اند. مسیر جبرانی احتمالی باید وابسته به همان درخواست/پورت، با بررسی و تأیید دقیق جداگانه باشد؛ نه retry خودکار یا Enable/config-save.

### F-03 — ticket یک‌بارمصرف نیست: تأیید، متوسط

ارجاع: R2 E3، R3 A-02.
کد: `equipment_ops.py:80–99, 221–233`.

همان ticket در دو درخواست recover تا پیش از expiry دوباره به executor رسید و هر دو 200 شدند. comment «one-time» با پیاده‌سازی سازگار نیست. صدور در یک ثانیه برای همان user/host/username/interface نیز ticket یکسان تولید می‌کند؛ nonce تصادفی ندارد.

اما این نتیجه به معنی «هر replay قطعاً دوباره پورت سالم را bounce می‌کند» نیست: helper واقعی pre-check دارد و اگر پورت دیگر err-disabled نباشد، write نمی‌کند. خطر در تداوم/بازگشت خطا و هم‌زمانی واقعی است. این مسیر همچنان login، permission، scope، HMAC و credential تجهیز می‌خواهد؛ شاهد bypass آن‌ها نیست.

اصلاح باید شامل شناسهٔ یکتای تأیید، TTL و مصرف اتمی باشد. صرف افزودن used-set به توکن فعلی می‌تواند check تازه در همان ثانیه را هم به اشتباه مصرف‌شده بداند. رمز دستگاه یا خروجی CLI نباید در state مصرف ticket ذخیره شود. رفتار failure/uncertain باید روشن باشد: برای ادامه، تأیید تازه لازم است.

### F-04 — قفل سمت سرور برای recovery وجود ندارد: تأیید، متوسط

ارجاع: R2 E4، R3 A-03.
کد: handler recover در ops؛ Waitress با threads=16 در `app.py:847`؛ UI سریالی.

دو درخواست معتبر هم‌زمان، با دو نشست همان کاربر و ticket همان پورت، واقعاً هم‌زمان وارد executor ساختگی شدند (max_active=2). سریالی‌بودن رابط و سقف پنج انتخاب، کنترل هم‌زمانی سمت سرور نیست. این بازتولید، اثبات interleave فیزیکی IOS نیست، ولی نبود guard را ثابت می‌کند.

قفل فقط per-interface ممکن است برای چند interface یک سوئیچ کافی نباشد؛ per-host برای جلسه‌های config محافظه‌کارانه‌تر است. با قفل باید consumption ticket و آزادسازی در finally هماهنگ باشد. در استقرار فعلی تک‌پردازه، guard حافظه‌ای ممکن است کافی باشد؛ برای چند پردازه/instance، dict یا Lock محلی تضمین سراسری نمی‌دهد. سقف کلی SSH نیز باید با ظرفیت و timeoutها تنظیم شود، نه عدد حدسی به‌عنوان benchmark قطعی.

### F-05 — backup با مدیر سفارشی: تأیید، متوسط و دارای اثر استقرار

ارجاع: R2 S1، R3 A-05؛ مرتبط با R1 H-04.
کد: `manage.py:34`، `windows/preflight_backup.py:27` در مقابل `app.py:148–149, 551–552, 797`.

با **خود API واقعی مدیریت کاربران**، مدیریت به حساب سفارشی جدید منتقل و مدیر قدیمی حذف شد؛ هیچ دست‌کاری مستقیم SQL برای ایجاد این وضعیت لازم نبود. حساب جدید role=4 و manage-users معتبر داشت، login و create_app آن را قبول کردند؛ با این حال manage.check، backup عادی و preflight backup همگی No active administrator دادند.

اثر فقط backup دستی نیست؛ backup روزانه، preflight نصب و اعتبارسنجی restore نیز می‌توانند متوقف شوند. وجود integrity_check و SQLite Backup API تأیید شد؛ ادعای «شاید اصلاً integrity check نداریم» رد می‌شود. مشکل، مدل تشخیص مدیر است.

اصلاح باید semantics احراز مدیر را با runtime یکسان کند و JSON معیوب/حساب غیرفعال را fail-closed نگه دارد؛ صرف وجود substring manage-users در متن JSON کافی نیست. preflight عمداً dependency-free است؛ import سادهٔ app.py/Flask در آن ممکن است پیش‌نیاز جدید و خطای نصب بسازد. این ملاحظه باید در طراحی اصلاح رعایت شود.

### F-06 — masking status ضعیف‌تر از descriptions است: تأیید با پیش‌شرط مشخص

ارجاع: R3 A-04، R1 H-05؛ همچنین یافتهٔ تکمیلی این داوری.
کد: `_clean_description` در `probe.py:162–167`، `errdisabled_interfaces:215–227`، `safe_status_ports:462–468` و `descriptions_table:475–498`.

بازتولیدها:

1. عین credential در Name پاک می‌شود؛ نسخهٔ متفاوت از نظر بزرگ/کوچکی حروف باقی می‌ماند.
2. **نام پیش از مقایسه به ۱۲۸ نویسه کوتاه می‌شود.** در fixture معتبرِ دارای credential بلند در Name، خروجی ۱۲۸ نویسهٔ آغاز همان credential را نگه داشت، چون دیگر رشتهٔ کامل برای مقایسه وجود نداشت.
3. Name دارای الگوی community/secret-like در status mask نمی‌شود، در حالی که همان الگو در descriptions پاک می‌شود.

پیش‌شرط: مقدار حساس از قبل در Name/Description تجهیز آمده باشد. این، نشت خودکار هر رمز از env به کاربر دیگر نیست؛ و در passwordهای case-sensitive، تغییر case لزوماً عین رمز واقعی نیست. طول/نمایش Name روی مدل واقعی IOS نیز اینجا آزمایش نشده است. با این حال ضعف قرارداد masking و نمونهٔ truncation در parser فعلی واقعی‌اند.

جهت اصلاح: تشخیص حساسیت روی متن خام، قبل از truncation، هماهنگی casefold و الگوهای شناخته‌شده در مسیرهای مرتبط، سپس خروجی bounded. محافظت کامل در برابر همهٔ رازهای ناشناخته یا مقدارهایی که خود تجهیز قبلاً truncate کرده تضمین‌شدنی نیست؛ نباید هر IP یا نام عادی مالک پورت را خودکار «secret» فرض کرد.

### F-07 — نوع switch در API الزام نشده: رفتار تأییدشده، طبقه‌بندی وابسته به سیاست محصول

ارجاع: R2 E2.
کد: `app.py:592–599` در مقابل `switches()` رابط تجهیزات.

روتر شناخته‌شدهٔ داخل region مجاز با executor ساختگی check=200 گرفت؛ همان کاربر برای region خارج از scope، 403 گرفت و executor صدا نشد. پس **این شاهد دورزدن scope یا احراز هویت نیست**. همهٔ روترها هم الزاماً show interfaces status معتبر ندارند و mock این سازگاری را اثبات نمی‌کند.

اگر workflow بناست فقط سوئیچ باشد، backend باید محدودیت معنایی kind=switch را برای رکورد شناخته‌شده نیز اعمال کند، نه فقط UI. نوع‌های سفارشی باید با kind پایدار سنجیده شوند، نه نام نمایشی. در IP دستیِ دارای پنج wildcard، از IP به‌تنهایی نمی‌توان نوع سخت‌افزار را فهمید؛ نباید بدون مجوز command discovery اضافه کرد یا ادعا کرد همان محدودیت فیزیکی را اثبات کرده‌ایم.

### F-08 — host key: accept-new برابر strict نیست

ارجاع: R2 E8، R3 H-02.
کد: `probe.py:275–280`، `app.py:489` و `windows/start.ps1:22`.

چک host key خاموش نیست، اما مقدار پیش‌فرض **accept-new / TOFU** است: کلید اولین تماس ثبت و تغییر بعدی رد می‌شود. در strict/yes، کلید باید از قبل تأیید شده باشد. هر توصیف قبلی من که حالت فعلی را معادل strict با کلید ازپیش‌تأییدشده القا کرده باشد، دقیق نبوده است.

برای شبکهٔ حساس، ثبت و تأیید مستقل fingerprint و strict توصیه می‌شود. first-contact MITM محدودیت امنیتی واقعی TOFU است، نه رخداد نفوذِ مشاهده‌شده در این محیط. start.ps1 مقدار policy را بدون شرط روی accept-new می‌گذارد؛ بنابراین تنظیم env بیرونی به strict به‌تنهایی کافی نیست و مسیر startup هم باید با سیاست انتخاب‌شده هماهنگ شود. known_hosts یا خطای کلید را برای راه‌انداختن اتصال حذف/نادیده نگیریم.

### F-09 — مستندات قدیمی Connector: تأیید، کم‌خطر عملیاتی

ارجاع: R3 A-07.
`docs/PRIVATE_APPLICATION_BOUNDARY_FA.md` هنوز در پذیرش استقرار از مسیر VDI می‌گوید، در حالی که startup و probe فعلی مستقیم از سرور SSH می‌زنند. باید اصلاح شود. این نه دلیل بازگرداندن Connector است و نه دلیل تغییر معماری فعلی.

## ۶. مواردی که نباید با اصلاح شتاب‌زده بدتر شوند

### کلید ticket پس از restart

ابطال ticket پنج‌دقیقه‌ای با restart یک انتخاب امن است. در استقرار فعلی یک process و چند thread، نیاز به فایل دائمی برای صحت کارکرد نشان داده نشده است. کلید پایدار، replay را رفع نمی‌کند و تأیید قبل از restart را زنده نگه می‌دارد. اگر روزی چند process/instance نیاز شد، کلید مشترک به‌تنهایی هم کافی نیست؛ مصرف ticket و lock باید مشترک/اتمی باشند. نمونهٔ R1 با Get-Random و فایل کلید بدون طراحی ACL و lifecycle نباید بی‌بررسی کپی شود؛ برای راز رمزنگاری از CSPRNG استفاده می‌شود.

### inspect و header توضیحات

`inspect_device` اگر مرز description header نباشد fail-closed می‌کند و دوباره وصل نمی‌شود؛ در diagnostic هم یک read و descriptions_unreadable دیده شد. اگر مرز وجود داشته باشد ولی خود description خراب باشد، status معتبر حفظ می‌شود. این محدودیت عملیاتی است، نه false-clean. جداکردن خطای description از status مفید است فقط وقتی مرز/کامل‌بودن status قابل اثبات باشد. به‌جای حدس parser یا retry خودکار auth، مسیر read-only /check موجود می‌تواند با اقدام صریح و مجاز اپراتور استفاده شود.

### quoting فایل known_hosts

`-o` صرفاً یک آرگومان خام برای SSH نیست؛ محتوایش توسط parser پیکربندی SSH دوباره parse می‌شود. readconf.c از argv_split با quote handling استفاده و UserKnownHostsFile را لیست مسیرها می‌خواند. پس نبود shell دلیل حذف quote داخلی نیست؛ حذف آن ممکن است یک مسیر دارای فاصله را به چند فایل بشکند. ssh -G محلی هر دو ورودی را پذیرفت، اما خروجی متنی آن مرزبندی لیست را روشن نمی‌کند. هیچ bug Win32 قطعی یا رفع‌شدن آن را ادعا نمی‌کنم؛ round-trip واقعی مسیر فاصله‌دار روی Windows باید آزمایش شود.

### پردازش detached و timeout

deadlineهای معمول helper از timeout والد کوتاه‌ترند و در حالت عادی kill/cleanup داخلی داریم. این تضمینِ cleanup پس از crash/OOM/kill بیرونی نیست. سناریوی orphan روی Windows هنوز آزمایش نشده است. **CREATE_NO_WINDOW به‌تنهایی جای kill-tree/Job Object را نمی‌گیرد** و تغییر flags ممکن است رفتار ASKPASS را عوض کند. هر تغییر supervision باید با تست واقعی بدون راز/روی تجهیز آزمایشگاهی مجاز سنجیده شود.

### IIS و فایل legacy

updater فایل قدیمی www/FAM.html را باقی می‌گذارد، ولی web.config فعلی آن URL را قبل از static serving به Flask دارای کنترل نشست rewrite می‌کند. بنابراین «در پیکربندی درست، UI حتماً public است» اثبات نشده. باقی‌ماندن فایل، ضعف دفاع در عمق و وابستگی به قواعد درست است. حذف آن هم ساده نیست: updater فعلی وجودش را برای اعمال پچ لازم می‌داند و rollback از آن استفاده می‌کند. cleanup باید هم‌زمان با اصلاح idempotency/rollback و تست واقعی IIS انجام شود، نه حذف دستی تک‌فایل.

### rate-limit، KDF و CSP

- rate-limit فعلی پشت ARR عمدتاً per-username است؛ یک کاربر داخلی می‌تواند همان username را موقتاً lock کند. XFF جعلی نباید تصمیم امنیتی شود؛ اعتماد به proxy نیاز به overwrite در ARR، trusted proxy محدود و تست واقعی دارد.
- PBKDF2 با 210k و حداقل طول ۴، سیاست‌هایی قابل تقویت‌اند. افزایش بدون versioning/benchmark ممکن است hashهای قدیمی را ناسازگار یا CPU را تحت فشار بگذارد؛ بهبود باید نسخه‌دار و تدریجی باشد.
- CSP فعلی script-src ندارد؛ این فرصت hardening است، نه اثبات وجود XSS. policy سخت‌گیرانه روی bundle دارای inline script بدون migration/nonce می‌تواند کل برنامه را از کار بیندازد.

### Excel

در مسیر XLSX بررسی‌شده، SheetJS رشته‌های آغازشده با =/+/@ را به‌عنوان سلول رشته‌ای بدون f ذخیره/بازیابی کرد؛ تست موجود نیز این رفتار را پوشش می‌دهد. افزودن apostrophe به همهٔ نام‌ها بدون اثبات نیاز می‌تواند مقدار و round-trip داده را تغییر دهد. دربارهٔ CSV، exportهای دیگر یا تفسیر همهٔ نسخه‌های Excel حکم کلی نمی‌دهیم؛ آن مسیرها باید جدا سنجیده شوند. هیچ payload اجرایی یا برنامهٔ Excel واقعی اجرا نشد.

## ۷. ترتیب اصلاح پیشنهادی — هنوز اجرا نشده

1. **Bootstrap امن برای نصب fresh**؛ بدون reset کاربران/DB موجود و بدون رمز در argv/log/plaintext file.
2. **کنترل recovery به‌صورت یک مجموعه:** nonce و مصرف اتمی ticket + قفل per-host + نتیجهٔ recovery_uncertain/توقف batch در حالت نامشخص. این‌ها مستقل از هم کامل نمی‌شوند.
3. **اصلاح backup/preflight و سازگاری مدیر سفارشی**؛ چون می‌تواند خود زنجیرهٔ نصب/بازیابی امن را مختل کند.
4. **هماهنگ‌سازی masking پیش از truncation** و casefold/الگوهای حساس با تست‌های دقیق.
5. **تطبیق سیاست switch-only، strict host-key provisioning و مستندات استقرار**؛ بدون ازبین‌بردن دسته‌های پویا یا قابلیت IP دستی مجاز.
6. بعد از آن hardening مرحله‌ای proxy/rate-limit، KDF، CSP و lifecycle پردازش با تست واقعی Windows/IIS.

تمام اصلاح‌های بعدی باید در فایل‌های واقعاً مستقرشدنی و allowlist/hashهای بسته‌بندی هم منتقل شوند؛ اصلاح manage/preflight صرفاً در checkout بدون قرارگرفتن در مسیر آپدیت، روی سرور اثری ندارد. بعد از هر تغییر، قراردادهای امنیتی جدید، تست‌های مثبت/منفی و برابری payload پچ با سورس باید دوباره تأیید شوند.

## ۸. ارزیابی کیفیت خود گزارش‌ها

- **R1:** به علت استخراج ناقص و نبود اجرای تست، پوشش محدودتر است. بعضی مشاهده‌ها مفیدند، اما «۷ bug تأییدشده» ترکیبی از bug، style، محدودیت سازگاری و مشکل بسته است. پیشنهاد فوری پایدارکردن ticket key و حذف کل کلاس تست، اولویت‌های درستی برای این کد نیستند.
- **R2:** گزارش کامل‌تر از خلاصهٔ پیام است؛ ۹۶ تست و شواهد کد آن را تقویت می‌کنند. نکتهٔ قطع ارتباط و backup مهم است. نوع switch و ریسک IIS/Excel باید با قیود بالا تفسیر شوند. توصیهٔ کلید پایدار و تغییر flags را بی‌آزمایش نمی‌پذیرم.
- **R3:** replay، concurrency، bootstrap، masking و backup یافته‌های مفید و قابل بازتولیدند. محدودیت‌های تست را عمدتاً صریح گفته است. استدلال quoting کافی نیست و ماسک case-insensitive به‌تنهایی نقص truncation را حل نمی‌کند.

**نتیجه:** نه تأیید کلی هر سه گزارش درست است و نه رد کلی آن‌ها. ایرادهای واقعی باید اصلاح شوند؛ تغییرهای خطرناک یا صرفاً سلیقه‌ای باید از آن‌ها جدا بمانند. هیچ یک از این بررسی‌ها سازگاری واقعی Windows OpenSSH/RADIUS/IOS/IIS یا یکسان‌بودن نصب فعلی با سورس را اثبات نمی‌کند.
