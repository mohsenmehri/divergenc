#### Finding ID: FINDING-01
**Category:** Logic Error / Missed Valid Signals  
**Severity:** Critical  
**Exact location:** `v2_research_export_v2.mq5` — خطوط 17001 تا 17014 (در تابع `EvaluateArmedDivergencePipeline`)  
**What the code does:**  
هنگامی که یک دایورجنس مسلح (Armed Divergence) فعال است و قیمت سطح Reclaim یا BOS را می‌شکند (`bos || reclaim` درست می‌شود)، کد بررسی می‌کند که آیا RSI کندل جاری (`rsi1`) بالای سطح شکست `rsi_failure_level` است یا خیر. اگر در همان کندل اول `rsi1 <= rsi_failure_level` باشد، کد بلافاصله دستور `g_armed_divergence.Reset()` را اجرا می‌کند.  

**Why it may be wrong:**  
شکست قیمت در کندل $N$ رخ می‌دهد، اما اندیکاتور RSI ممکن است ۱ یا ۲ کندل دیرتر (در کندل $N+1$ یا $N+2$) از سطح failure swing عبور کند. ریست کردن فوری `g_armed_divergence` در همان کندلی که شرط RSI برقرار نشده، کل Setup را برای همیشه پاک می‌کند. در کندل‌های بعدی که RSI بالا می‌رود، دیگر `g_armed_divergence.active` برابر `false` شده و سیگنال کلاً نابود می‌شود.  

**Concrete counterexample:**  
1. در کندل ۱۰، دایورجنس صعودی تایید و مسلح می‌شود (`rsi_failure_level = 55.0`).  
2. در کندل ۱۲، قیمت سقف کندل P3 را می‌شکند (`reclaim = true`)، اما RSI در کندل ۱۲ برابر ۵۴.۰ است ($54.0 \le 55.0$).  
3. کد `g_armed_divergence.Reset()` را می‌زند و setup پاک می‌شود.  
4. در کندل ۱۳، قیمت بیشتر رشد کرده و RSI به ۵۸.۰ می‌رسد ($58.0 > 55.0$). اما چون setup در کندل ۱۲ پاک شده، هیچ معامله‌ای باز نمی‌شود.  

**Expected result:**  
تا زمانی که قیمت سطح P3 Low را نشکسته (Invalidation)، Setup مسلح بماند و منتظر تایید RSI در کندل‌های بعدی باشد.  

**Actual/potential result:**  
از دست رفتن حجم زیادی از سیگنال‌های کاملاً معتبر و سودده.  

**Impact on signal or backtest:**  
تعداد tradeهای بک‌تست به شدت و به‌طور کاذب کاهش یافته و نتایج استراتژی غیرواقعی می‌شود.  

**Confidence:** High (100%)

- P2

6.2. تفسیر عملی
implementation فعلی سه pivot را مدل می‌کند، نه سه divergence pair مستقل.
پس از نظر رفتاری، pattern به این صورت بازسازی می‌شود:
Bullish

- سه pivot low هم‌جهت: P1, P2, P3
- قیمت: به سمت lowهای پایین‌تر حرکت می‌کند
- oscillator: به سمت lowهای بالاتر حرکت می‌کند

Bearish

- سه pivot high هم‌جهت: P1, P2, P3
- قیمت: highهای بالاتر
- oscillator: highهای پایین‌تر

6.3. آیا «divergence اول/دوم/سوم» در کد وجود دارد؟
به‌صورت literal، نه.
آنچه در کد می‌بینیم:
1. divergence بین P1 و P2
2. divergence بین P2 و P3
3. سپس geometry کلی P1..P3
پس implementation فعلی:

- دو leg pairwise دارد
- به‌علاوه یک ارزیابی aggregate سه-pivotی
- نه سه divergence pairwise مستقل

7) شرایط divergence اول، دوم، سوم
7.1. divergence اول
استنباط از کد:

- بین P1 و P2
- برای bullish: قیمت lower low و RSI higher low
- برای bearish: قیمت higher high و RSI lower high

7.2. divergence دوم

- بین P2 و P3
- همان منطق جهت‌دار

7.3. divergence سوم
در implementation attach‌شده divergence سوم pairwise مستقلی دیده نمی‌شود.

چیزی که به‌جای آن وجود دارد:

- validation کلی سه-pivot
- span/gap/ratio/features/filterها
- armed pipeline

بنابراین اگر spec بیرونی پروژه واقعاً «سه divergence کامل پشت سر هم» باشد، این implementation با آن هم‌معنا نیست.
8) رابطه زمانی بین سه جزء pattern
ترتیب

- P1 قدیمی‌تر از P2
- P2 قدیمی‌تر از P3

فاصله مجاز
از ورودی‌های دیده‌شده:

- inp_min_pivot_gap_between = 3
- inp_max_pivot_span_p1_p3 = 25

interpretation

- بین pivotهای متوالی حداقل gap لازم است
- از P1 تا P3 حداکثر span مجاز است

آیا max gap مجزای P1→P2 و P2→P3 دیده شد؟
من از شواهد Attach‌شده فقط min gap و max total span را با اطمینان استخراج می‌کنم.

قید صریح دیگری را بدون spec خارجی حدس نمی‌زنم.
9) confirmation / invalidation / reset
9.1. confirmation
باید سه لایه را از هم جدا کنیم:
A) confirmation pivot
pivot فقط بعد از بسته شدن barهای راست confirmed می‌شود.
B) confirmation pattern
وقتی P3 هم confirmed شد و geometry/filterها pass شدند، الگو وارد حالت armed می‌شود.
C) confirmation signal
signal بلافاصله با دیدن P3 لزوماً fire نمی‌شود.

بلکه:

- pattern first becomes armed
- بعد EvaluateArmedDivergencePipeline() تصمیم نهایی می‌گیرد

9.2. invalidation

- live geometry هر tick ممکن است از بین برود
- armed divergence ممکن است clear یا replace شود
- min-bars-between-signals مانع re-fire سریع می‌شود

اما spec بیرونی مستقل برای invalidation در Attachments وجود ندارد، پس:

- invalidation رفتاریِ “مقصود استراتژی” را نمی‌توان قطعی‌تر از این گفت.

9.3. reset

- rolling pivot state
- armed divergence state
- setup step state (ResetStepData)
- live geometry flags

13) state machine بازسازی‌شده
حالت S0 — Idle

- هنوز pivot کافی برای pattern وجود ندارد

حالت S1 — One pivot

- اولین pivot معتبر سمت bullish یا bearish ثبت شده

حالت S2 — Two pivots

- P1, P2 ثبت شده‌اند
- divergence leg اول قابل بررسی است

حالت S3 — Three pivots candidate / confirmed pattern

- P3 نیز ثبت شده
- divergence دوم و geometry کلی بررسی می‌شود
- اگر pass شود → armed

حالت S4 — Armed divergence

- g_armed_divergence
- pipeline منتظر confirmation / profile pass است

حالت S5 — Signal fired

- FireSignal(...)
- setup ساخته می‌شود

حالت S6 — Active setup lifecycle

- step management
- pending entries / fills / progression / stop / target

حالت S7 — Finalized / reset

- setup بسته شده
- step state reset
- divergence state ممکن است clear شود یا pivot rolling ادامه یابد

parallel side-branch — Live P3 visualization

- مستقل از مسیر confirmed
- intrabar
- ephemeral
- repaintable
- برای نمایش/monitoring مفید، نه لزوماً همان trade trigger

## مرحله 2 — Code Reconstruction (Trace کامل مسیر)

### 2.1 Input data

- `OnTick()` (خط 46830): تشخیص کندل جدید با `iTime(...,0) != last_bar` → `ProcessNewBar()`.
- `ProcessNewBar()` (47133): `Bars < MIN_BARS_REQUIRED(300)` → return. سپس `copy_cnt = min(bars-10, 500)` و `g_tf[0].CopyIndicatorBuffers(copy_cnt)`.
- بافرها همه به‌صورت series از index 0 (کندل در حال شکل‌گیری) کپی می‌شوند: `CopyBuffer(handle, buf, 0, count, buffer)` (7522).

### 2.2 RSI

دو منبع RSI هم‌زمان وجود دارد:

- **RSI استاندارد**: `handle_rsi` (iRSI) → `buffer_rsi`.
- **VA-RSI** (Volatility-Adjusted، پورت از Pine): `CalculateVARSI()` (7630) — از `close/ATR` نرمالایز می‌کند، seed = SMA روی قدیمی‌ترین پنجره موجود، سپس بازگشتی به سمت index 1؛ `buffer_varsi[0] = buffer_varsi[1]` (آینه کردن کندل نیمه‌کاره).
- **انتخاب‌گر واحد**: `DIV3_RSIAtShift(shift)` (15369) — `shift<1` را رد می‌کند، اول VA-RSI، fallback به RSI استاندارد.

### 2.3 Pivot / Swing detection

- `DetectPivots()` (16150): یک کاندید در هر بار، در `chk = test_right + 1`.
    - `test_left = g_pivot_left + extra_left`, `test_right = g_pivot_right + extra_right` (extraها فقط در `DIV3_PRECISION_HYBRID + require_multiscale`).
    - guard: `chk_time <= g_last_pivot_check → return` (یک‌بار در هر بار).
    - سمت چپ: `chk+1 .. chk+test_left`؛ سمت راست: `chk-1 .. chk-test_right` با clamp `sh < 1 → reject`. **پس دورترین بار سمت راست = shift 1 = آخرین کندل بسته‌شده.**
    - فیلترها: ATR availability → `DIV3_ProminenceATR` → `DIV3_PassesSameSideExcursion` → `DIV3_SelectAlignedRSI` → RSI gate.
- `DIV3_SelectAlignedRSI()` (15383): پنجره `pivot_shift ± tol` با `tol = min(inp_div3_rsi_alignment_tolerance, confirmed_right)`؛ حالت `PIVOT_ANCHOR_BOTH_CONFIRMED` نیاز دارد RSI هم در `±inp_pivot_right_bars` extreme باشد.
- `DIV3_RegisterPivot()` (16104): ذخیره در ring buffer `g_pivots[MATRIX_SIZE=500]` و **همچنین در آرایه‌های فقط‌سه‌عضوی** `g_bull_pivots[3]` / `g_bear_pivots[3]` با shift-left. `confirm_time = iTime(...,1)`.

### 2.4 Divergence detection

`CheckDivergence()` (17076) — فقط روی **سه پیوت آخر همان سمت**:

- Bull: `price_ok = p0<p1<p2` (LLL) و `rsi_ok = r0>r1>r2` (strict) یا `r0 > max(r1,r2)` (relaxed).
- Bear: آینه (HHH + RSI نزولی).
- گیت‌های کمکی: `inp_min_rsi_delta`، `inp_min_price_delta_atr`، zone filter، `CheckRSIRange`، OB confluence، `inp_use_pivot_distance_filter` (dc/d01/d12/span).

### 2.5 Divergence sequencing

**نکته ساختاری مهم:** آنچه کد پیاده کرده «سه واگرایی مستقل پشت سر هم» نیست؛ یک **الگوی سه‌پیوتی واحد** است (P1→P2→P3 با price LLL/HHH و RSI در جهت مخالف). هیچ شمارنده‌ای برای «divergence #1 / #2 / #3» و هیچ state machine مجزا برای دنباله‌ی واگرایی‌ها وجود ندارد. sequencing فقط از طریق ترتیب زمانی سه پیوت آخر (`s2>s1>s0`) تأمین می‌شود.

### 2.6 State management

- `g_armed_divergence` (struct `SArmedDivergence`, 12668) — **تک اسلات** (single slot). `ArmThreePivotDivergence()` (16845) آن را پر می‌کند؛ `confirmed=true` از `CheckDivergence`، `confirmed=false` از `CheckLiveThreePivotDivergence`.
- سطوح مشتق: `structure_level` (اکسترمم بین P2 و P3)، `reclaim_level` = High/Low خود کندل P3، `rsi_failure_level` = اکسترمم RSI در shift 2..s3-1.
- dedup: `g_last_bull_p1_time/p2_time`, `g_last_bull_sig_time`, `g_last_signal_time`, cooldown بر حسب بار.

### 2.7 Third divergence / Signal generation

- `EvaluateArmedDivergencePipeline()` (16959) روی هر تیک ولی یک‌بار در هر بار (`last_eval_bar`): invalidation → BOS/Reclaim → RSI failure → H1 regime → volatility(M1 ATR + MTF DI) → `FireSignal(bull, 1, "PROFILE_...")`.
- `FireSignal()` (17919): `entry = iLow/iHigh(shift=1)`، `atr = buffer_atr[1]`، snapshot، QC، ladder 5 پله، BE/TP، ثبت shadow/registry.
- `ManageSetups()`/`CheckTakeProfit()`/`ManagePositions()` مدیریت پله‌ها را با tick + `iHigh/iLow(0)` انجام می‌دهند.

1. **DIV-01 را رفع کنید:** بررسی ابطال باید در هر کندل انجام شود (حتی وقتی setup فعال است)، بر پایه‌ی running min/max از `armed_time`، به‌علاوه یک حداکثر سن (بار) برای `g_armed_divergence`. سپس بک‌تست ۱۱ ساله را دوباره اجرا کنید — هرگونه optimization روی نتایج فعلی روی ورودهای zombie fit می‌شود.
2. **DIV-03 را رفع کنید:** `if(out_shift - rb < 1) return false;` تا پنجره‌ی تأیید RSI متقارن و همگن شود.
3. **DIV-02 را رفع کنید:** P3 زنده باید از همان selector (`DIV3_RSIAtShift`-equivalent) استفاده کند. اگر `DIV3_LIVE_P3_ONLY` هرگز استفاده نمی‌شود، آن مسیر را صریحاً غیرفعال/حذف کنید تا آمار را آلوده نکند.
4. **DIV-04 را رفع کنید:** تشخیص پیوت را time-based با catch-up کنید و شمارنده‌ی بارهای skip شده اضافه کنید تا اختلاف live/backtest قابل اندازه‌گیری شود.

**C. سؤالات طراحی که باید تصمیم‌گیری شوند (نه لزوماً bug)**

1. آیا `reclaim_level` = High کندل P3 عمدی است؟ اگر بله، توصیف سیستم باید از «ورود پس از تأیید ساختاری» به «ورود در بازگشت از P3» تغییر کند، چون تفسیر edge کاملاً متفاوت است. (DIV-06)
2. آیا سطوح ladder/TP باید از fill محاسبه شوند یا از اکسترمم کندل سیگنال؟ پاسخ، همه‌ی معیارهای R و نرخ TP1 را تغییر می‌دهد. (DIV-08)
3. آیا محدودیت «حداکثر یک setup آرم‌شده / یک setup فعال» بخشی از spec است؟ اگر بله، نرخ سیگنال گزارش‌شده باید با نرخ `ARMED_WAIT_ACTIVE_SETUP` و `SUPERSEDED_*` همراه شود. (DIV-07)
4. آیا اجرای بدون SL سمت بروکر برای live قابل قبول است؟ توزیع MAE و max-step در ۱۱ سال را ارائه کنید، نه فقط PnL. (RISK-A)
5. ترتیب فراخوانی `CopyIndicatorBuffers` با depthهای متفاوت (500 در `ProcessNewBar` vs 100 در گیت‌ها) را بازبینی کنید و تأیید کنید که هیچ خواننده‌ای بعد از resize به index > 99 نیاز ندارد. (RISK-D)
